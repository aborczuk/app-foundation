# HUD: T027 - Build a project-local MCP stdio backend server that owns warm semantic query and rerank operations in `src/mcp_codebase/` and wire it in `.codex/config.toml`

## Objective

Deliver `T027` so the accepted project-local MCP stdio path stops being only a persistence probe and becomes the real warm backend host for semantic query and rerank operations.

This task is the server-side half of the migration. It does not switch `read_code` over yet; it builds the MCP backend contract and wiring that `T028` will consume.

## Relevant Domains

- `Code Reading and Discovery`: the new MCP backend must host the expensive semantic query and rerank work that `read_code` currently owns through the repo-local worker.
- `Performance`: this task exists to move startup-heavy backend ownership into the proven persistent MCP server process.
- `Governance`: the accepted transport is the project-local MCP stdio server, not another socket daemon and not the per-invocation worker.

## Candidate Design Slices

- `Slice PL-05 - Daemon Lifecycle, Observability, and Live Proof` — keep the live-proof identity contract and extend it into the real backend host without losing observability.
- `Slice PL-07 - Daemon-Owned Remaining First-Search Startup` — move warm semantic query service ownership and rerank ownership into one long-lived backend while keeping the synchronous client path minimal.

## Proposed Solution

- Replace the probe-only MCP server with a real project-local MCP backend server module under `src/mcp_codebase/` that exposes bounded operations for:
  - backend identity / health
  - rerank scoring
  - semantic query
- Reuse the existing `VectorIndexService` ownership pattern already implemented in `src/mcp_codebase/index/reranker_stdio_worker.py` rather than inventing a second backend stack.
- Update `.codex/config.toml` so the project-local MCP server entry points to the real backend server module while preserving the persistent stdio lifecycle already proven by `get_process_identity`.
- Keep the existing persistence identity contract available from the new backend server so `T026` evidence and later live proofs still work.

## Current Repo Behavior

- `.codex/config.toml` currently registers only `read_code_persistence_probe`, which runs `src.mcp_codebase.persistence_probe_server`.
- `src/mcp_codebase/persistence_probe_server.py` currently exposes one FastMCP tool, `get_process_identity`, and nothing for query or rerank work.
- `scripts/read_code.py` still starts its own repo-local stdio subprocess, `src.mcp_codebase.index.reranker_stdio_worker`, and sends `score` / `query` JSON requests directly over that private pipe.
- `src/mcp_codebase/index/reranker_stdio_worker.py` already owns a warm `VectorIndexService` and supports `health`, `score`, `query`, and `shutdown`, but only as a repo-local subprocess protocol rather than a project-local MCP server.

## Target Behavior

- One project-local MCP stdio server owns the warm `VectorIndexService` for both semantic query and rerank.
- The server preserves the identity proof contract from `T026` while adding bounded query and score operations that later tasks can call.
- No new socket daemon, file-RPC path, or second warm backend process is introduced.
- The exact seam at `src/mcp_codebase/persistence_probe_server.py:get_process_identity` either remains available or is replaced by an equivalent identity operation on the new backend server so persistence verification stays valid.
